# Functional design: async calls
## Objectives

It's often useful to be able to delay a function call until some other event occurs. The most obvious example is a network request to another service that can take unpredictably long to wait for the response of.

## Proposed solution

Allow defining named functions on the top level of pluggable object declarations. Supported pluggable object types are: workflow rules, http handlers. Whenever there's a need to call an async function, it is referred to by name. The execution context of the async function is the same as that of the calling site, additionally, it should be possible to pass extra parameters to the async function by adding them to the context.
It's a strict requirement that the async function is defined in a different syntax context than the function that calls them, which implies that it should be defined in the pluggable object's own declaration.

### Example

```
exports.rule = entities.Issue.onChange({
  title: 'Title',
  guard: (ctx) => {
    return true;
  },
  action: (ctx) => {
    ctx.store('usr', ctx.currentUser); // storing a parameter that will be available to the functions called later
    
    // example 1
    new http.Connection('https://example.com')
      .postAsync('', null, JSON.stringify({'issueId': ctx.issue.id}), 'responseHandler'); // mind the last parameter
    // It's a part of the contract of connection.postAsync that it puts the response into the context, the response does not need to be persisted   
  },
  requirements: {
    State: {
      type: entities.State.fieldType,
      SentToExternalSystem: {}
    }
  },
  asyncFunctions: {
    responseHandler: (ctx) => {
      if (ctx.response.isSuccess) {
        ctx.issue.fields.set(ctx.State, ctx.State.SentToExternalSystem);
        console.log(`Issue ${ctx.issue.id} sent to example.com on behalf of ${ctx.load('usr').login}`);
      }
      // example 2
      ctx.invokeAsync('justAFunction', 5000, ctx.issue.issueId); // use issue id as deduplicaton key
    },
    justAFunction: (ctx) => {
      console.log(ctx.issue.id);
    }
  }
}
```

### Why so complex?

Implementing it via just a regular callback function passed directly into the postAsync (as well as getAsync, putAsync, deleteAsync, etc) function wouldn't work as the GraalVM context of the execution is bound to the current thread and not available in the asynchronous function.
The following
```
const u = issue.Assignee;
new http.Connection('https://example.com')
      .postAsync('', null, JSON.stringify({'issueId': ctx.issue.id}), (ctx) => { console.log(u.login) });
```
will not work because of the access to the local variable *u*. To make it work, the current GraalVM context needs to be reserved until the async function gets called, which can lead to resource starvation.

## Implementation details

### Execution context

- All attributes available in the context to the entry point function (workflow rule/http handler) are available to the async functions
- Async functions are executed in the same GraalVM context pool as the entry point function (which implies security and time sandboxing)
- The current user is the same for async functions as for the entry point function

### Storage

- Execution context should be persisted in the DB between call site and function invocations. After all the async functions are invoked, the context is to be cleaned up
- In case N async calls are scheduled, the context is persisted N times, each time with a set of attributes that were available at the time of the scheduling
- Stored attributes can be primitives or entities
- Null/undefined value of a stored context attribute is indistinguishable absence of value
- A new PersistentExecutionContext class to be defined, its instances are created each time an async invocation is scheduled and contain references to the context attributes of an entity type and directly store primitive attributes. Each PersistentExecutionContext instance also has a reference to the one previously created, which allows reducing stored data duplication effectively providing a snapshotting mechanism

### Calling sequence and exception handling

- A function, either the entry point or an async function, can async-call only zero or one other functions (ctx.invokeAsync or http.*Async). The total number of all async calls triggered from a single entry point is limited to 10. Each invocation of an on-schedule rule's action function starts an async chain, i.e. for every issue processed it's possible to have up to 10 async invocations. When exceeded, an exception is thrown
- asyncCall as well as asyncGet/Post/etc do not return anything. The reason is the same mentioned in the *Why so complex?* paragraph
- Async calls are executed sequentially in the order they were triggered
- Async calls are executed each in a new R/W transaction
- If function A async-calls a function B, the invocation of the latter only starts when the transaction in which the former was executing, commits successfully
- If any of the called functions throws an exception, then all async calls that have not yet happened are canceled. Already running, an async call can finish
- Any exceptions thrown from an async function are logged to the logger associated with the initial entry point

### API

- httpConnection.postAsync and similar functions return nothing and put the 'response' (defined in http.js) object in the context. This context attribute does not need to be persistent (and can be accessed simply via ctx.response), as the async function is called exactly when the response has been received. These functions do not support delayed execution, which means the execution starts as soon as the current transaction finishes
- ctx.invokeAsync is a special function that allows calling any function defined in the asyncFunctions section of the pluggable object declaration. Its signature is ctx.invokeAsync(functionName, delay, deduplicationKey). The first parameter is required; the default value for the second parameter is 0, max value is 1 week, which means the scheduler will not wait any extra time after the transaction of the current function commits. The third parameter is an optional deduplication key (string). When a non-empty key is provided, any existing pending async call with the same key within the same entry configuration (rule + project pair) is replaced — the old call is deleted and the new one is scheduled with a fresh delay. This enables "debounce" semantics: repeated calls with the same key reset the timer so only the last call executes. When the key is null or empty, the call is scheduled unconditionally (default behavior). Already-executed calls are not affected — if the previous call has already run and been cleaned up, the new call is scheduled normally
- ctx.load and ctx.store load and store context attributes. JS attributes of the ctx objects are not persistent, except for those available in the original ctx object at the moment of the initial entry point invocation (e.g. ctx.currentUser)

## Implementation notes

### Removing stale persistent contexts

Persistent contexts are removed after the very last async invocation triggered by an entry point. Also, a watchdog is to be implemented that will remove the stale persistent contexts i.e. those that waited for a week + time buffer

### ctx.store/ctx.load vs PersistentEvalParamsAdapter

PersistentEvalParamsAdapter is a deprecated adapter for long-lived plugin configuration (settings). It wraps XdAbstractPluginConfiguration and persists values as XdPluggedAttribute entities. It is meant to survive across rule invocations indefinitely.

The proposed ctx.store/ctx.load is for short-lived execution context that exists only for the duration of an async call chain and is cleaned up when all async functions complete. These are conceptually different:

- **Lifetime**: PersistentEvalParamsAdapter = permanent config; ctx.store/load = ephemeral per-chain
- **Scope**: PersistentEvalParamsAdapter is scoped to a plugin configuration; ctx.store/load is scoped to a single entry-point invocation
- **Cleanup**: PersistentEvalParamsAdapter values are never auto-cleaned; ctx.store/load values must be cleaned after the chain completes

The XdPluggedAttribute type hierarchy (string, long, double, boolean, entity reference) solves the same "store primitives and entities" problem that PersistentExecutionContext needs. PersistentExecutionContext could be modeled similarly — a Xodus entity holding a collection of typed attribute values — but should be a separate entity class with its own lifecycle, not reuse XdAbstractPluginConfiguration.

### Reusing on-schedule rules runtime

Several components from the on-schedule rules infrastructure are directly reusable:

- **LocalJob + AbstractLocalJobProcessor**: base class for job submission, thread pool execution, lifecycle tracking. Async function execution can extend LocalJob.
- **ExecutionContext.captureLocal()**: preserves tenant/user context across threads. Required for any async work — captures at scheduling time, restores at execution time.
- **SingleContextPool**: sequential GraalVM context access (one context, one-at-a-time). Matches the "sequential async calls" requirement. However, async functions need to share the context pool of the originating pluggable object rather than creating a new one.
- **Per-item transactional(isNew = true)**: new R/W transaction per work unit, exactly what the spec requires for each async function call.
- **contextPool.canEnter() guard**: prevents concurrent access to a GraalVM context, ensuring sequential execution.

What needs to be different:

- On-schedule rules use Quartz cron triggers. Async functions need event-driven triggers (HTTP response received, delay elapsed). For ctx.invokeAsync with a delay, a ScheduledExecutorService or Quartz one-shot trigger would work. For HTTP response callbacks, the trigger is the completion of the HTTP call.
- On-schedule rules iterate over issues from a search query. Async functions execute a single named function with a stored context.

Suggested approach: create a new AsyncFunctionJob extending LocalJob, and a new AsyncFunctionJobProcessor extending AbstractLocalJobProcessor with a dedicated thread pool. The processor already supports delayed submissions.
